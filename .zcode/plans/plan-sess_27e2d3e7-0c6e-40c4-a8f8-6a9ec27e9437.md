# 自研跨平台 IM（Android / Windows / Linux / Web）

## 已确认的决策
- 客户端：**Kotlin Multiplatform + Compose Multiplatform**（Android、Desktop JVM 覆盖 Win/Linux、Web 用 Wasm——CMP 1.9 起 Wasm 已 Stable）
- 服务端：**Go**，完全自研，参考 OpenIM / WuKongIM 的架构设计
- 音视频：**全自建**（LiveKit SFU + coturn），桌面端通话分阶段（一期只做 Android + Web）
- 部署：**私有化 Docker Compose 一键部署**
- MVP 范围：注册登录 + 单聊 + 离线消息 + 群聊 + 多媒体消息 + 音视频通话

## 参考的开源项目
- **OpenIM**（Go）：分层架构（gateway 接入层 / logic 业务层 / 消息投递与 seq 机制）、消息可靠性模型
- **WuKongIM**（Go）：轻量长连接网关设计、seq 离线同步
- **Turms**：消息模型与数据分片思路（只参考设计不抄代码）

## 服务端架构（Go）

**核心组件**
1. **Gateway**（`gorilla/websocket` 或 `gobwas/ws`）：维持客户端长连接，心跳保活，鉴权（登录后发 token），上行消息 → 投递，下行推送。单机多路复用，后续可水平扩展（Redis pub/sub 跨节点投递）。
2. **Logic**（HTTP API，`chi` router）：注册/登录（argon2 密码哈希 + JWT）、好友关系、群组管理、历史消息查询。
3. **存储**：MySQL 8（用户/好友/群/消息历史，消息表按 conversation 分片或按月分表）、Redis（会话 token、在线状态、未读数、seq 分配原子操作）。
4. **对象存储**：MinIO（图片/文件/语音/视频附件，客户端预签名 URL 直传）。

**消息可靠性模型（参考 OpenIM 的 seq 机制）**
- 每个会话（单聊/群聊）维护单调递增 seq（Redis INCR）
- 发送流程：client → gateway → logic（落库 + 分配 seq）→ ACK（带 seq）→ 投递给在线接收者
- 接收方确认收到后本地记录 max seq；断线重连后按「本地 max seq → 服务端最新 seq」拉增量（拉补机制），保证不丢不重
- 消息 ID 用服务端雪花 ID；客户端消息状态机：sending → sent(ACK) / failed
- 协议：WebSocket 二进制帧 + Protobuf（connect/auth/msg_send/msg_send_ack/msg_notify/msg_pull/heartbeat）

**音视频**
- SFU 用 **LiveKit**（Go 编写、Apache-2.0、可自托管，与后端同语言生态）
- 自己的 Go 服务只做**通话信令**（invite/accept/reject/cancel/timeout 走 IM 消息通道），收到 accept 后用 LiveKit Server SDK 签发 room token，客户端拿 token 直接连 LiveKit
- coturn 提供 STUN/TURN，打通 NAT
- 客户端 WebRTC：Android 用 `webrtc-android`（Stream 维护的预编译库）、Web 用浏览器原生 WebRTC；桌面端**一期不接**（JVM 无成熟 libwebrtc 绑定，二期补）

## 客户端架构（KMP）

```
shared (KMP library)
├── commonMain
│   ├── protocol/     # Protobuf 生成代码 + WebSocket 客户端封装（Ktor ws）
│   ├── db/           # SQLDelight：消息、会话、联系人本地缓存
│   ├── domain/       # 会话管理、消息状态机、seq 同步、重连退避
│   └── feature/      # 各功能的 Presenter/State（Compose 可直接消费）
├── androidMain / desktopMain / wasmMain   # actual 实现：通知、文件路径、剪贴板、音视频采集
composeApp    # 一套 Compose UI 跑四端（会话列表、聊天页、通讯录、设置、通话 UI）
```

- 网络层 Ktor（支持 Android/桌面/Web 三种 engine），DB 用 SQLDelight（支持 Android SQLite / JVM SQLite / Web sql.js+WASM）
- 状态管理用 kotlinx-coroutines Flow，UI 层 `collectAsStateWithLifecycle` 思路

## 实施里程碑

**M1 — 协议与服务端地基**
proto 协议定义（connect/auth/msg/heartbeat）→ Go gateway + logic 骨架 → MySQL/Redis schema → 注册登录 + JWT 鉴权 → WebSocket 长连接 + 心跳

**M2 — 消息核心**
单聊收发 + seq/ACK + 落库 → 离线拉补（重连增量同步）→ 会话列表/未读数 → 客户端 KMP 骨架（四端可编译运行）+ 聊天 UI 跑通真机

**M3 — 群聊 + 多媒体**
群组 CRUD + 群消息扇出（写扩散按群规模选择：小群写扩散、大群读扩散）→ 群 @提醒 → MinIO 预签名直传 + 图片/文件/语音消息 → 客户端缓存与断点续传策略

**M4 — 音视频（Android/Web）**
LiveKit + coturn 部署 → 通话信令（invite/accept/reject/timeout，响铃/取消/挂断状态机）→ Android & Web 端 1v1 通话 UI 与接通

**M5 — 交付**
docker-compose 一键部署全部组件 → 端到端联调（Android ↔ Web ↔ 桌面消息互通）→ 部署文档 + 协议文档

## 关键风险与预案
1. **Web 端 WASM 的 SQLDelight/Ktor 兼容性**：M1 末先用最小 spike 验证三端 actual 实现，有问题 Web 端退化用 IndexedDB 封装
2. **桌面音视频**：已确认分阶段，M4 只承诺 Android/Web，桌面通话列二期
3. **群消息扇出量级**：MVP 按小群（≤200）写扩散实现，预留读扩散接口
4. **CMP Wasm 首载体积**：开启 WasmGC + 压缩，可接受范围内不再过度优化

## 交付后的验证方式
- `docker compose up` 起全套服务
- Android 真机 / 桌面运行 / 浏览器打开 Web 版，注册两个账号互相收发消息（含离线、群聊、图片）
- Android 与 Web 之间发起 1v1 通话验证音视频链路
